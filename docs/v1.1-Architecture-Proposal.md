\# 1. Vision



GH-AIOS (Greenhouse AI Operating System) is the intelligent software platform that powers Greenhouse Futures Lab and its ecosystem of initiatives.



Rather than functioning as a single AI assistant, GH-AIOS is designed as a collection of modular services that work together through clearly defined responsibilities. Each service performs one specific function while relying on shared platform capabilities such as knowledge retrieval, routing, and data management.



The long-term objective is to create an AI operating system that is reliable, maintainable, scalable, and easy to extend without requiring major architectural redesigns.



Every architectural decision should support four primary goals:



\- Simplicity over unnecessary complexity.

\- Clear separation of responsibilities.

\- Independent evolution of services.

\- Long-term maintainability.



This proposal defines the architectural direction for GH-AIOS v1.1 while preserving compatibility with the stable v1.0 release.





\# 2. Design Principles



The GH-AIOS architecture is governed by a small set of engineering principles that ensure the platform remains understandable, maintainable, and scalable as it evolves.



\## 2.1 One Service, One Responsibility



Every service exists to perform one clearly defined responsibility.



Services should not perform unrelated tasks or duplicate the responsibilities of other services.



This principle makes the platform easier to maintain, test, and extend.



\---



\## 2.2 Modular by Design



Every major capability should exist as an independent service.



Services communicate through well-defined interfaces rather than tightly coupling their internal logic.



This allows individual services to evolve or be replaced without affecting the rest of the platform.



\---



\## 2.3 Core Services Before Features



Platform capabilities that are shared across multiple services should be implemented as Core Services rather than duplicated within Specialist Skills.



Examples include:



\- Knowledge Retrieval

\- Query Generation

\- Knowledge Acquisition



Specialist Skills consume these capabilities instead of rebuilding them.



\---



\## 2.4 Knowledge as a Shared Resource



All Specialist Skills should rely on a common organizational knowledge base rather than maintaining separate sources of information.



This ensures consistency across the platform and prevents conflicting outputs.



\---



\## 2.5 Separation of User Interaction and Platform Operations



User-facing workflows should remain independent from background platform operations.



Examples:



User-facing



\- AI Gateway

\- Content Service

\- Festival Service



Background



\- Knowledge Acquisition

\- Data Synchronization

\- Maintenance Jobs



This separation improves performance and keeps user interactions responsive.



\---



\## 2.6 Version First



Architectural changes should be introduced through versioned releases.



Stable releases remain unchanged while new functionality is developed in the next version.



This provides predictable evolution and reliable rollback points.



\---



\## 2.7 Documentation Before Implementation



Every significant architectural change should be documented and reviewed before implementation begins.



Documentation serves as the reference for development rather than being written afterwards.



\---



\## 2.8 Simplicity Over Complexity



The preferred solution is the simplest design that satisfies the current requirements.



Complexity should only be introduced when it provides clear long-term value.





\# 3. System Architecture Layers



GH-AIOS is organized into logical architectural layers.



Each layer has a clearly defined responsibility and communicates only with the layers that are relevant to its function.



This layered approach improves maintainability, simplifies debugging, and allows the platform to evolve without unnecessary coupling between services.



\---



\## Layer 1 — Gateway



The Gateway Layer is the single entry point into GH-AIOS.



Its responsibility is to receive requests, understand user intent, and route each request to the appropriate Specialist Skill.



Responsibilities:



\- Receive user requests

\- Determine user intent

\- Route requests to the correct service

\- Coordinate communication between services



Current Service:



\- AI Gateway



The Gateway Layer does not perform business logic, create content, conduct research, or manage knowledge.



\---



\## Layer 2 — Core Services



Core Services provide shared platform capabilities that every Specialist Skill depends upon.



They are not user-facing services.



Instead, they provide foundational functionality that powers the rest of the system.



Current Core Services:



\- Knowledge Retrieval Service

\- Query Generator



Planned Core Services (v1.1):



\- Knowledge Acquisition Service



Future Core Services:



\- Memory Service

\- Security Service

\- Planning Service

\- Analytics Service



Core Services should never duplicate the responsibilities of Specialist Skills.



\---



\## Layer 3 — Specialist Skills



Specialist Skills perform domain-specific work.



Each Specialist Skill owns one business capability.



Current Specialist Skills:



\- Content Service

\- Festival Service

\- Research Service

\- Sponsorship Service

\- Publishing Service



Specialist Skills may consume Core Services but should remain independent from one another wherever possible.



\---



\## Layer 4 — Knowledge Layer



The Knowledge Layer is the shared organizational memory of GH-AIOS.



It stores structured knowledge that can be retrieved by any Specialist Skill through the Knowledge Retrieval Service.



Current components include:



\- PostgreSQL

\- PGVector

\- Organizational Documents

\- Knowledge Chunks

\- Embeddings



The Knowledge Layer is considered the single source of truth for organizational information.



\---



\## Layer 5 — Delivery Layer (Future)



The Delivery Layer is responsible for executing actions outside GH-AIOS.



Examples include:



\- LinkedIn

\- Instagram

\- Gmail

\- WhatsApp

\- Website CMS



Delivery Services do not generate decisions or create content.



They only execute approved actions produced by Specialist Skills.





\# 4. Data Flow



GH-AIOS is designed around controlled information flow.



Information moves through clearly defined services, ensuring that each component has a single responsibility and that knowledge remains consistent across the platform.



The platform distinguishes between two independent operational flows:



\- User Request Flow

\- Knowledge Acquisition Flow



These flows intersect only through the Knowledge Layer.



\---



\## 4.1 User Request Flow



The User Request Flow handles every interaction initiated by a user.



```

User

&#x20;  ▼

&#x20;  │

&#x20;  ▼

&#x20;  │

&#x20;  ▼

Response

```



The AI Gateway never communicates directly with the Knowledge Layer.



All knowledge access occurs through the Knowledge Retrieval Service.



\---



\## 4.2 Knowledge Acquisition Flow



The Knowledge Acquisition Flow operates independently from user requests.



Its responsibility is to continuously improve the organizational knowledge base.



```

&#x20;       │

&#x20;       ▼

&#x20;       │

&#x20;       ▼

&#x20;       │

&#x20;       ▼

Chunk Generation

&#x20;       │

&#x20;       ▼

Embedding Generation
```

Knowledge Acquisition may be triggered by:



\- Scheduled execution

\- Manual execution

\- RSS updates

\- Website monitoring

\- Document uploads

\- Future API integrations



\---



\## 4.3 Knowledge Ownership



The Knowledge Layer has a single write path.



Only the Knowledge Acquisition Service is permitted to create, update, or modify organizational knowledge.



All other services consume knowledge through the Knowledge Retrieval Service.



This guarantees:



\- Consistent organizational knowledge

\- Controlled knowledge quality

\- Easier auditing

\- Simplified maintenance

\- Reduced duplication





\# 5. Service Responsibilities



Every service within GH-AIOS owns a single business capability.



Services communicate through clearly defined interfaces and should never assume responsibilities that belong to another service.



This separation ensures that GH-AIOS remains modular, maintainable, and scalable.



\---



\## 5.1 AI Gateway



Purpose



Acts as the single entry point into GH-AIOS.



Responsibilities



\- Receive all user requests.

\- Determine user intent.

\- Route requests to the appropriate Specialist Skill.

\- Coordinate service execution.



Does NOT



\- Generate content.

\- Conduct research.

\- Retrieve knowledge directly.

\- Publish content.

\- Modify the Knowledge Layer.



\---



\## 5.2 Knowledge Acquisition Service



Purpose



Continuously discover, collect, validate, and ingest knowledge into the Knowledge Layer.



Responsibilities



\- Search trusted websites.

\- Monitor RSS feeds.

\- Process uploaded documents.

\- Extract webpage content.

\- Clean and normalize data.

\- Detect duplicates.

\- Generate metadata.

\- Create semantic chunks.

\- Generate embeddings.

\- Update the Knowledge Layer.



Supported Sources



\- Trusted websites

\- RSS feeds

\- PDFs

\- Internal documents

\- Research reports

\- Government publications

\- Future APIs



Does NOT



\- Respond to user requests.

\- Generate business outputs.

\- Route requests.

\- Publish content.



\---



\## 5.3 Knowledge Retrieval Service



Purpose



Provide relevant organizational knowledge to Specialist Skills.



Responsibilities



\- Search the Knowledge Layer.

\- Retrieve relevant context.

\- Support all Specialist Skills.



Does NOT



\- Modify knowledge.

\- Acquire new information.

\- Generate responses.



\---



\## 5.4 Query Generator



Purpose



Transform natural language into optimized retrieval queries.



Responsibilities



\- Expand search intent.

\- Improve semantic search accuracy.

\- Optimize retrieval requests.



Does NOT



\- Search databases.

\- Retrieve knowledge.

\- Generate final outputs.



\---



\## 5.5 Content Service



Purpose



Create written communication.



Responsibilities



\- LinkedIn posts

\- Instagram captions

\- Blog articles

\- Newsletters

\- Email copy

\- Marketing copy



Does NOT



\- Publish content.

\- Perform independent research.

\- Modify the Knowledge Layer.



\---



\## 5.6 Festival Service



Purpose



Support festival planning and operations.



Responsibilities



\- Programme design

\- Scheduling

\- Logistics

\- Event planning

\- Operational planning



Does NOT



\- Publish announcements.

\- Generate sponsorship proposals.

\- Write marketing content.



\---



\## 5.7 Research Service



Purpose



Produce structured research and analytical outputs.



Responsibilities



\- Research summaries

\- Climate analysis

\- Reports

\- Fact checking

\- Comparative analysis



Does NOT



\- Create marketing content.

\- Ingest knowledge.

\- Publish results.



\---



\## 5.8 Sponsorship Service



Purpose



Support fundraising and strategic partnerships.



Responsibilities



\- Sponsorship proposals

\- Partnership outreach

\- Sponsor packages

\- Partnership communications



Does NOT



\- Plan festivals.

\- Publish campaigns.

\- Conduct research outside sponsorship needs.



\---



\## 5.9 Publishing Service



Purpose



Deliver approved content to external platforms.



Responsibilities



\- Publish content

\- Schedule posts

\- Execute content delivery

\- Manage publishing workflows



Does NOT



\- Create content.

\- Edit content.

\- Perform research.

\- Plan campaigns.





\# 6. Service Interaction Model



Services within GH-AIOS communicate through well-defined interaction paths.



To maintain a modular architecture, direct dependencies between services should be minimized. Wherever possible, services interact through Core Services rather than communicating directly with one another.



This approach reduces coupling, improves maintainability, and allows services to evolve independently.



\---



\## 6.1 User Request Interaction



The User Request Interaction represents the primary execution path through GH-AIOS.



```

User

&#x20;  │

&#x20;  ▼

AI Gateway

&#x20;  │

&#x20;  ▼

Specialist Skill

&#x20;  │

&#x20;  ▼

Knowledge Retrieval Service

&#x20;  │

&#x20;  ▼

Knowledge Layer

&#x20;  │

&#x20;  ▼

Specialist Skill

&#x20;  │

&#x20;  ▼

Response

```



Every user request enters through the AI Gateway.



The AI Gateway determines user intent and routes the request to the appropriate Specialist Skill.



If organizational knowledge is required, the Specialist Skill retrieves it through the Knowledge Retrieval Service before generating a response.



\---



\## 6.2 Knowledge Acquisition Interaction



Knowledge Acquisition operates independently of user requests.



```

Trusted Sources

&#x20;       │

&#x20;       ▼

&#x20;       │

&#x20;       ▼

&#x20;       │

&#x20;       ▼

&#x20;       │

&#x20;       ▼

Validation

&#x20;       │

&#x20;       ▼

Chunk Generation

&#x20;       │

&#x20;       ▼

Embedding Generation

&#x20;       │

&#x20;       ▼

Knowledge Layer

```



Knowledge Acquisition may be triggered through:



\- Scheduled execution

\- Manual execution

\- Document uploads

\- RSS feed updates

\- Website monitoring

\- Future API integrations



Knowledge Acquisition never responds directly to users.



\---



\## 6.3 Publishing Interaction



Publishing occurs only after content has been created and approved.



```

Specialist Skill

&#x20;       │

&#x20;       ▼

Publishing Service

&#x20;       │

&#x20;       ▼

Delivery Platform

```



Examples of delivery platforms include:



\- LinkedIn

\- Instagram

\- Gmail

\- WhatsApp

\- Website CMS



Publishing Services execute delivery only.



They do not create or modify content.



\---



\## 6.4 Service Communication Rules



To preserve architectural integrity, all services must follow these rules:



\- Every user request enters through the AI Gateway.

\- AI Gateway routes requests only to Specialist Skills.

\- Specialist Skills retrieve organizational knowledge only through the Knowledge Retrieval Service.

\- Only the Knowledge Acquisition Service may modify the Knowledge Layer.

\- Specialist Skills should not communicate directly with one another unless explicitly required by an approved workflow.

\- Publishing Services communicate only with approved external delivery platforms.

\- Core Services must remain independent from Specialist Skills whenever possible.



These interaction rules establish predictable communication paths throughout GH-AIOS and reduce unnecessary coupling between services.

\- Architecture

\# 10. Architectural Laws



The Architectural Laws define the fundamental rules that govern the design, implementation, and evolution of GH-AIOS.



These laws are non-negotiable and apply to every service, workflow, and future architectural decision. Any exception must be formally documented and approved as part of a future architecture revision.



\---



\## Law 1 — Single Entry Point



Every user request must enter GH-AIOS through the AI Gateway.



The AI Gateway is the sole entry point responsible for receiving requests, understanding user intent, and routing requests to the appropriate Specialist Skill.



No Specialist Skill may accept user requests directly.



\---



\## Law 2 — Single Knowledge Writer



Only the Knowledge Acquisition Service is permitted to create, modify, or update the Knowledge Layer.



All other services consume organizational knowledge exclusively through the Knowledge Retrieval Service.



This ensures a single source of truth and protects the integrity of the platform's knowledge base.



\---



\## Law 3 — One Service, One Responsibility



Every service owns one primary business capability.



Services should perform their designated responsibility exceptionally well rather than attempting to solve multiple unrelated problems.



Responsibilities must not overlap without explicit architectural justification.



\---



\## Law 4 — Documentation Before Implementation



Architectural changes must be documented, reviewed, and approved before implementation begins.



Documentation serves as the blueprint for development, ensuring that implementation follows design rather than defining it.



\---



\## Law 5 — Stable Releases Are Immutable



Released versions of GH-AIOS represent stable milestones in the platform's evolution.



Stable releases may receive critical bug fixes where necessary but must never be restructured or fundamentally redesigned.



Architectural improvements belong in the next version of the platform.



\---



\## Law 6 — Reuse Before Reinvention



Before introducing a new service, workflow, or capability, existing platform services must be evaluated for reuse or extension.



Duplicate functionality should be avoided unless there is a clear architectural reason to create a separate service.



A simpler, reusable solution is always preferred over unnecessary complexity.



\---



\## Law 7 — Knowledge Is a Shared Asset



Organizational knowledge belongs to the platform, not to individual services.



Every Specialist Skill should consume knowledge from the shared Knowledge Layer to ensure consistency, reduce duplication, and maintain a unified understanding across the entire GH-AIOS ecosystem.



\---



\## Law 8 — Design for Evolution



Every architectural decision should make GH-AIOS easier to extend in the future.



The platform should evolve by adding or improving modular services rather than rewriting existing functionality.



Scalability, maintainability, and simplicity must guide every design decision.
